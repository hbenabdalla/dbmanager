# DB Manager 0.13.0

**DB Manager 0.13.0** completes roadmap milestone 0.13 — **Performance Intelligence** — and fixes
every defect found by the first full real-engine run of 0.12.0 against official vendor images.
Upgrading from 0.12.0 is automatic (migration `0011`); no configuration change is needed.

## Highlights

### Alerts that know what is normal for each server

Alert rules can now fire on a **deviation from the server's own baseline** instead of a fixed
number: `zscore(cpu.percent, 7d baseline) > 3` fires when CPU is three standard deviations above
what is normal for *that* server. The baseline needs at least 60 samples, excludes the window
being tested, and the rule wizard shows the baseline before you save.

### Which statement got slower — and did its plan change?

**Queries → Regressions** lists statements whose mean latency in the last hour (configurable) is
well above their baseline, with relative and absolute thresholds and a minimum number of
executions so noise is not reported. On **Oracle** and **SQL Server** it also reports **plan
changes** (Oracle's dominant plan hash, SQL Server's cached plan count). Each regression becomes a
recommendation (`GEN-PERF-011`) that resolves itself when the statement is back to normal.

### When will it fill?

**Monitoring → Capacity forecast** forecasts storage per **server, database and tablespace** with a
robust trend (Theil–Sen: a one-off bulk load or purge does not distort it), a **90 % band**, and
three readings of *days to full*: earliest, likely and latest. Rule `GEN-PERF-012` warns when the
earliest reading is within 30 days. Nothing is forecast from less than 7 days of history, a flat
trend or an unknown capacity — the reason is shown instead.

### Compare periods and plans

**Queries → Compare periods** compares statement activity between two periods (last 24 h vs the
same day a week ago, …): slower, faster, new and gone statements, ranked by the change of total
time. **Queries → Compare plans** puts two saved plans side by side — cost, operators, access-path
changes per table and plan issues that appeared or were resolved. Save a plan with *Save plan as*
on Execution plans.

### Did the fix help?

When a recommendation is resolved, DB Manager measures the metric (or the statement latency) that
triggered it for 24 hours before and after, and records **improved**, **unchanged** or
**regressed**. **Optimization → Outcomes** summarizes the results.

## Real-engine validation

The integration suite ran on Docker against PostgreSQL 16, MySQL 8.4, MariaDB 11.4, SQL Server
2022, Oracle Database 21c XE, Db2 LUW 11.5, OpenLDAP, Keycloak 26 and Vault 1.17 with
least-privilege accounts. The engine-by-engine result, including what is *not* validated, is in
the [real-engine validation report](../product/real-engine-validation.md); the defects found and
their fixes are in [real-engine findings](../troubleshooting/real-engine-findings.md); the exact
grants are in [database permissions](../database-permissions/index.md).

Fixed in this release:

- PostgreSQL restores onto servers older than the client tools (`transaction_timeout`).
- MySQL restores of triggers and routines with binary logging on (error 1419): checked first,
  refused with the fix.
- Restores of objects owned by other definers (MySQL, MariaDB) without `SUPER`.
- SQL Server backup metadata readable by a `db_backupoperator`; SQL Server, Oracle and Db2 backup
  errors reported as backup errors.
- Db2 restore command with the log target; LDAP groups listed once.

## Upgrade

```bash
git pull && docker compose up -d --build
```

Migration `0011` adds the z-score rule setting, the recommendation validation record and saved
plans. The upgrade test seeds users, role assignments, servers, credentials, alert rules,
channels, findings, backup targets and policies and settings at the 0.12.0 schema and checks
that every row survives.

## Known limitations

See the [changelog](https://github.com/hbenabdalla/dbmanager/blob/main/CHANGELOG.md) and the
[roadmap](../product/roadmap.md#known-limitations-of-the-current-release). In short: plan changes
only for Oracle and SQL Server; no seasonality in forecasts; database and tablespace forecasts
start after 7 days of history; before/after validation shows correlation, not proof; Oracle TCPS
and replica topologies not exercised; Db2 for z/OS needs external validation.
