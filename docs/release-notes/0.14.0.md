# DBManager 0.14.0

**DBManager 0.14.0** completes roadmap milestone 0.14 — **Reporting** — and gives the product its
visual identity: the DBManager logo throughout the product and documentation, and one engine mark
per database engine wherever servers are shown. Upgrading from 0.13.0 is automatic (migration
`0012`); no configuration change is needed.

## Highlights

### Reports people actually send

Four new reports join the catalog:

- **Security findings** — every finding with severity, status, affected object, first and last
  seen, resolution date and remediation; filter by status and minimum severity.
- **Query statistics** — the heaviest statements in a window you choose (1 hour to 31 days):
  calls, total / mean / max time, the statement's share of the server's time, rows, CPU and reads.
- **Query regressions** — statements slower than their own baseline, with plan changes on Oracle
  and SQL Server.
- **Capacity forecast** — growth trend with a 90 % band and days to full, per server, database or
  tablespace.

Every report now takes an environment, an engine or a server as scope, and **Preview** shows the
first 50 rows before you download. Query text is masked in every report.

### PDF, rendered on the server

Every report downloads as **PDF** as well as CSV. The PDF carries the DBManager logo, who it was
generated for, when, the scope and the row count; the table header repeats on every page and wide
tables switch to landscape. The footer of every page says the file contains data visible to that
account. The CSV remains the complete export (the PDF lists up to 5,000 rows), and CSV values that
a spreadsheet would execute as formulas are now neutralised.

### Scheduled reports, with the owner's access

**Reports → Schedules** e-mails a report daily, weekly or monthly, at a time in your time zone, to
the recipients of one or more e-mail channels. A five-step wizard sets the report and its
parameters, PDF or CSV, the schedule, the channels and who the report runs as.

A schedule **runs with its owner's access at every run** — the owner's roles are loaded again each
time. If the owner is disabled or deleted, or no longer has the report's permission, the run fails
with the reason and **nothing is sent**. Each run records its status per channel (recipients or the
delivery error), row count and size; **Send now** runs a schedule immediately; every delivery is
audited. Files above `DBM_REPORT_MAX_ATTACHMENT_MB` (10 MB) are not sent.

### A face for DBManager

The DBManager logo now appears on the sign-in page, in the setup wizard, in the sidebar (expanded
and collapsed), on the About page, on the loading and first-run screens, in PDF reports, in the
README and on the documentation site, with a new favicon, app icons and web app manifest. The logo
is used exactly as designed; on dark surfaces it sits on a light plate rather than being recoloured.

### One engine mark everywhere

A single `DatabaseEngineIcon` component replaces the letter badges in the fleet table and filters,
the server header, the dashboard's engine distribution, topology, search, alerts, findings and
recommendations, backup and restore, registration and onboarding, Engine support, Database drivers,
notification routing and the sign-in page. **Db2 LUW and Db2 for z/OS** have distinct marks, unknown
engines get a neutral fallback, and the engine name is always present as text or as the accessible
name.

These are **DBManager's own marks, not vendor logos**: the vendors' trademark policies do not permit
their logos in a third-party product without permission. Organisations licensed to use them can
place them in `DBM_BRANDING_DIR`; DBManager then shows them unaltered. See
[brand assets](../development/brand-assets.md).

## Upgrade

1. Back up the platform (**Backup & Restore → Back up now**, or `scripts/backup.sh`).
2. Pull or build the 0.14.0 images and restart. Migration `0012` runs automatically (new tables
   `report_schedules` and `report_runs`).
3. To schedule reports, grant `reports.schedule` (platform scope) — Platform Administrators have it —
   and make sure an e-mail notification channel exists.

**Compatibility notes**

- `GET /api/v1/reports` no longer returns `planned_formats`; every report has `formats: ["csv", "pdf"]`
  and a `params` list. `GET /api/v1/reports/{key}.pdf` now returns a PDF instead of `422`.
- The default MFA issuer (`DBM_MFA_ISSUER`) is now `DBManager`. Authenticator entries created
  before keep their label and keep working; set `DBM_MFA_ISSUER="DB Manager"` to keep the old label
  for new enrollments.
- Notification e-mail subjects and Teams card buttons now say *DBManager*.
- `scripts/backup.sh`, `restore.sh` and `restore-drill.sh` read `.env` without executing it, so
  values with spaces no longer need quoting.

## Validation

- Backend: unit, API and migration suites against PostgreSQL 16, including report delivery to a
  real SMTP server (aiosmtpd) and the upgrade of a 0.13.0 schema with data.
- Frontend: unit and component tests, type check and production build; visual check of the main
  pages in light and dark themes at 1440, 1280, 1024 and 820 px and with the collapsed sidebar.
- Real engines: PostgreSQL 16 adapter and backup suites re-run locally. Reporting reads data
  DBManager already collected and does not change any adapter; the full Docker matrix (MySQL,
  MariaDB, SQL Server, Oracle, Db2 LUW) is re-run with `scripts/integration-test` before publishing
  — see the [real-engine validation report](../product/real-engine-validation.md).

## Known limitations

- Scheduled reports are delivered by e-mail only; webhook channels cannot carry files.
- PDF reports list at most 5,000 rows and cut cells after 400 characters (the CSV has everything).
  No Excel format.
- Vendor logos are not bundled (see above).
- Unchanged from 0.13.0: LDAP validated against OpenLDAP, not Active Directory; Oracle TCPS not
  exercised; TLS certificate verification of target databases not real-validated; Db2 for z/OS
  requires external validation; no point-in-time recovery; Kubernetes manifests not validated in CI
  (milestone 0.15).
