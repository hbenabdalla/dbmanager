# DBManager 0.15.0

**DBManager 0.15.0** completes roadmap milestone 0.15 — **Cloud-Native Deployment**. DBManager now
installs on Kubernetes and OpenShift with one Helm command, from signed images with SBOMs, and
runs several API and worker replicas that start safely together, elect one scheduler leader and
show who is running. Connections to its own PostgreSQL and time-series store can be encrypted and
verified. Before any of this was built, the whole repository was validated again from scratch and
every failure was fixed at its root. Upgrading from 0.14.0 is automatic (migration `0014`).

## Highlights

### Helm chart for Kubernetes and OpenShift

```bash
helm install dbm oci://ghcr.io/hbenabdalla/charts/dbmanager --version 0.15.0 \
  --namespace dbmanager --create-namespace \
  --set secrets.masterKey="$(head -c32 /dev/urandom | base64)" \
  --set secrets.bootstrapAdminPassword='<a strong password>' \
  --set secrets.postgresPassword='<a strong password>' --set secrets.timeseriesPassword='<a strong password>'
helm test dbm -n dbmanager
```

- Two API, two worker and two frontend replicas by default, with PodDisruptionBudgets, topology
  spread and an optional autoscaler for the API.
- Bundled PostgreSQL and VictoriaMetrics for evaluation, or your own (managed PostgreSQL with
  `verify-full` TLS, an existing Secret from your secret manager).
- Every pod meets the **restricted** Pod Security Standard; `openshift=true` follows the
  restricted-v2 SCC and adds a Route. NetworkPolicies keep the databases private to DBManager.
- Install refuses missing secrets instead of inventing defaults.

Guide: [Kubernetes and OpenShift with Helm](../deployment/kubernetes-helm.md).

### Signed images and chart

Each release tag publishes the backend and frontend images and the chart to GitHub Container
Registry, signed with Sigstore cosign (keyless), with SBOM and SLSA provenance attestations, and
SPDX SBOM files on the GitHub release.

```bash
cosign verify ghcr.io/hbenabdalla/dbmanager-backend:0.15.0 \
  --certificate-identity-regexp 'https://github.com/hbenabdalla/dbmanager/.github/workflows/release.yml@refs/tags/v.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

### Replicas that coordinate — and that you can see

- Migrations and start-up work run under PostgreSQL advisory locks: a rolling upgrade or ten
  replicas starting at once is safe (before 0.15, replicas starting together on an empty database
  could fail).
- **Platform → Collectors → Deployment** lists every API and worker process with its pod name,
  version and last heartbeat, marks the scheduler leader, and warns about mixed versions, stale
  processes and a deployment with no worker. **About** shows a summary.
- When the leader dies another worker takes over within one scheduler tick. CI proves it twice:
  by killing a leader process, and by deleting the leader pod of a kind cluster.

Guide: [high availability](../deployment/high-availability.md).

### Internal TLS

- `DBM_DATABASE_TLS_MODE` (`require`, `verify-ca`, `verify-full`, …) and
  `DBM_DATABASE_TLS_CA_FILE` for the control-plane PostgreSQL. The backend CI now runs the API
  suite against a PostgreSQL that serves TLS, with `verify-full`.
- `DBM_TIMESERIES_TLS_CA_FILE` for an `https://` VictoriaMetrics.

### A clean validation first

Earlier test reports were not reused. The validation found and fixed
([details](../product/test-validation.md)):

- the Compose restore drill failing in CI (`scripts/backup.sh` used BusyBox `wget` options that
  do not exist);
- a MySQL 8.4 TLS test bug, and TLS missing from the MySQL and MariaDB test containers;
- LDAP StartTLS refused for servers addressed by IP (ldap3 ignored IP SANs);
- upgrade tests that did not start from the latest release, 0.14.0.

While 0.15 was built, review also caught the new About summary exposing the leader's host name
to every user; About now shows counts only.

## Upgrade notes

- Migration `0014` adds the `platform_instances` table (not part of platform backups).
- Nothing to configure for Docker Compose. For TLS to your own PostgreSQL, set
  `DBM_DATABASE_TLS_MODE=verify-full` and `DBM_DATABASE_TLS_CA_FILE`.
- If you used `deployment/kubernetes/`, consider moving to the chart; the manifests stay as a
  reference and now point at the published images.
- The frontend image builds on Node 24 and serves with nginx-unprivileged 1.31. For local
  frontend work use Node 24 (22.12 or later works).

## Testing

- Backend: 869 tests (684 unit, 164 API, 8 migration, 13 Helm chart), none skipped, against
  PostgreSQL 16 over TLS. Frontend: 183 tests; type check and build on Node 22 and 24.
- Real engines in the release environment: PostgreSQL 16, MariaDB 10.11 (TLS), VictoriaMetrics
  1.122 and OpenLDAP 2.6 (StartTLS): 35 passed. The full Docker matrix (MySQL, SQL Server, Oracle,
  Db2 LUW, Keycloak, Vault) runs on the release commit before the tag; Db2 for z/OS requires
  external validation ([real-engine report](../product/real-engine-validation.md)).
- Chart and manifests: lint, Kubernetes 1.29 and 1.31 schemas, restricted Pod Security and
  OpenShift checks; kind install, `helm test` and leader failover in CI. 41 pages of the running
  application rendered without errors.

## Known limitations

- The chart's bundled PostgreSQL and VictoriaMetrics are single instances for evaluation; use a
  managed or operator-run PostgreSQL in production. No operator, no VictoriaMetrics cluster chart.
- The chart was installed in kind only; OpenShift mode is checked against the restricted-v2 rules
  but not installed on an OpenShift cluster.
- Unchanged from 0.14.0: Db2 for z/OS requires external validation; Oracle TCPS not exercised;
  LDAP validated against OpenLDAP, not Active Directory; scheduled reports by e-mail only; no
  point-in-time recovery; cloud secret stores and native Azure/GCS targets planned.
