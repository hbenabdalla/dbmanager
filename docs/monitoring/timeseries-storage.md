# Time-series storage (VictoriaMetrics)

The fourth container, `database-manager-timeseries`, stores all monitoring history. See
[metrics-architecture.md](architecture.md) for why VictoriaMetrics was chosen.

## Container

| Setting | Value |
|---|---|
| Image | `victoriametrics/victoria-metrics:v1.122.0` (`DBM_TIMESERIES_IMAGE_TAG`) |
| Volume | `tsdata` → `/storage` |
| Network | `data` (internal): reachable only by the backend; **no published port** |
| Health check | `GET /health` (no credentials needed); backend waits for it to be healthy |
| Resources | `DBM_TIMESERIES_CPUS` (2), `DBM_TIMESERIES_MEMORY` (2g); `-memory.allowedPercent=60` |
| Restart | `unless-stopped` |
| Hardening | `no-new-privileges`, all capabilities dropped |

Flags and why:

| Flag | Purpose |
|---|---|
| `-retentionPeriod=${DBM_TIMESERIES_RETENTION:-90d}` | native retention ([retention.md](../administration/retention.md)) |
| `-dedup.minScrapeInterval=1ms` | identical (series, timestamp) samples stored once → retries and re-migration are idempotent |
| `-search.latencyOffset=5s` | new samples are queryable after ~5 s instead of the default 30 s |
| `-search.maxQueryLen=1MB` | fleet queries list many server ids |
| `-search.maxUniqueTimeseries` | per-query series limit (`DBM_TIMESERIES_MAX_UNIQUE_SERIES`, 1 M) |
| `-envflag.enable` | credentials come from the environment (`httpAuth_username`, `httpAuth_password`) and are not visible in the process list or `/flags` |

## Security

* Basic authentication on every data and admin endpoint; the password
  (`DBM_TIMESERIES_PASSWORD`) is generated by `scripts/init-env.*` and never hard-coded.
  Compose refuses to start without it.
* Not exposed: no host port, internal Docker network, a `NetworkPolicy` on Kubernetes.
* The browser never talks to it. The backend authorizes every request against PostgreSQL
  (RBAC scope by server id) **before** building a query, and the query is restricted to the
  allowed `server_id`s. Asking for a server outside the caller's scope returns no data.
* Stored values are numbers with bounded labels — no SQL text, credentials, session ids or
  error messages (label policy in `app/timeseries/model.py`).

Upgrading an existing installation: run `scripts\init-env.ps1` (Windows) or
`./scripts/init-env.sh` once. It appends the new settings to your `.env`, generates
`DBM_TIMESERIES_PASSWORD`, and keeps every existing value. Then `docker compose up -d --build`.

## Health and status

* `GET /readyz` reports `application`, `postgresql` and `timeseries` separately. Readiness
  depends only on PostgreSQL; a time-series outage sets `"degraded": true` but keeps the
  backend in service.
* **Platform → Monitoring storage** (permission `collectors.view`; changing the policy needs
  `settings.manage`): status, engine, version, series and sample counts, oldest and newest
  metric, retention in effect vs. policy, ingestion state (written, buffered, failed
  batches, dropped, last success/failure, last error), pending deletions.
* CLI: `python -m app.cli metrics status`.

## Deletions

Telemetry is deleted by stable labels only:

* server removed → `{server_id="<uuid>"}`;
* simulation removed → `{data_source="simulated"}`, plus a follow-up by the removed servers'
  ids.

Samples still buffered for those series are discarded, and the same deletion runs again
90 seconds later (global job `timeseries_deletes`, every minute) to catch a collection that
was already in flight in another worker. If the storage is unreachable the deletion is
queued in `app_settings` and retried every minute until it succeeds; a queued simulation
removal is stored by server id so it can never touch a newer simulated fleet.

## Migration from PostgreSQL (staged)

| Phase | What happens | Status |
|---|---|---|
| A | Time-series container, repository and batch writer deployed; reads still possible from both | done in this release |
| B | Collectors write only to the time-series DB (`DBM_METRICS_PG_DUAL_WRITE=true` keeps legacy writes during a trial) | done |
| C | Dashboards, APIs, recommendations, reports and simulation read the time-series DB | done |
| D | Copy history: `python -m app.cli metrics migrate-to-timeseries` | run once per installation |
| E | Verify: compare `metrics status` with the legacy row counts; spot-check charts of real servers | operator |
| F | Drop `metric_samples` and `query_stat_snapshots` (a later Alembic migration) | not yet — tables are kept and pruned by retention (`DBM_METRICS_RETENTION_DAYS`) |

### Migration tool

```bash
docker compose exec backend python -m app.cli metrics migrate-to-timeseries --dry-run
docker compose exec backend python -m app.cli metrics migrate-to-timeseries \
    [--batch-size 20000] [--from-date 2026-09-01] [--to-date 2026-10-01] [--server-id <uuid>] [--restart]
```

* **Progress** after every batch (rows done / total, percent).
* **Resumable**: the last migrated row id per table is checkpointed in `app_settings` after
  each batch (per filter combination); an interrupted run continues where it stopped.
  `--restart` ignores the checkpoint.
* **Idempotent**: original timestamps are kept and the storage deduplicates, so repeating a
  run never duplicates samples.
* Rows with unknown label keys are skipped and counted; query snapshots are merged per
  fingerprint exactly like live collection and their first/last seen dates are kept.
* Measured: 453,376 metric rows and 3,108 query rows migrated in 13 s; a second run resumed
  at the checkpoint and wrote nothing.
